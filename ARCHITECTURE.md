## 1. Назначение и согласованные решения

SoundMess — учебный музыкальный веб-сервис с полноценной демонстрацией основных пользовательских сценариев.

### 1.1. Возможности, которые уже реализованы

- Публичные каталоги треков, релизов и артистов.
- Прослушивание без регистрации.
- Нижний постоянный плеер, не прерывающийся при внутренних переходах.
- Очередь из треков текущей страницы, предыдущий/следующий трек, перемотка и громкость.
- Повтор текущего трека.
- Лайки и «Любимое» как единая функция.
- Приватные пользовательские плейлисты.
- Сохранение публичных релизов в медиатеку.
- Подписки на артистов и лента их публикаций.
- Комментарии с таймкодами и вложенными ответами.
- Учёт прослушиваний после 30 секунд фактического воспроизведения.
- Заявка на статус артиста.
- Загрузка аудио, обложки, текста и метаданных.
- Черновики и предварительная модерация треков и релизов.
- Кабинет артиста с аналитикой за 7/30 дней и топом-5 треков.
- Собственная панель модерации и управления аккаунтами.
- Виртуальный кошелёк, подтверждение пополнения, поддержка артиста и история операций.
- Адаптация интерфейса для телефона.
- Служебные команды проверки файлов, резервного копирования и создания демонстрационных данных.

### 1.2. Решения владельца, которые нужно сохранить

1. Проект учебный; производственная инфраструктура не была целью текущей реализации.
2. Гость может смотреть публичные страницы и слушать музыку.
3. Персональные действия требуют входа: лайки, подписки, комментарии, плейлисты, переводы.
4. Лайк сразу добавляет трек в «Любимое». Второй независимой системы избранных треков нет.
5. Сначала проверяется заявка артиста, затем каждый отправленный трек и каждый публичный релиз.
6. Музыка добавляется через загрузку файлов артистами.
7. Внешний импорт музыкального каталога отменён владельцем. Не восстанавливать его без новой задачи.
8. Донаты используют виртуальные средства. Реального платёжного провайдера нет.
9. Корзина и интернет-магазин не требуются.
10. В пользовательском интерфейсе используются названия «Кошелёк» и «Баланс», без приставки «демо».
11. Стиль — тёмный плоский интерфейс с оранжевым акцентом; ориентиром служили музыкальные сервисы.
12. Плашки треков — отдельные слегка прозрачные плитки с промежутками.
13. Основные кнопки плеера должны оставаться по центру; повтор размещён отдельно справа.
14. Перед важными изменениями, особенно операциями с данными и коммитами, владельца нужно предупредить.
15. Данные пользователя нельзя удалять ради «чистого» запуска.

Слово `demo` в имени служебной команды, тестовых аккаунтах и тестовых записях обозначает набор для демонстрации. Это не название кошелька.

## 3. Общая архитектура и асинхронность

### 3.1. Тип приложения

Это **Django-монолит с серверным рендерингом и улучшенной JavaScript-навигацией**.

Внутри одного Django-приложения `pc_store` находятся доменные модели, формы, выборки, сервисы, HTTP-обработчики и статические ресурсы.

Упрощённая схема запроса:

```text
Браузер
  |
  | GET страницы / POST формы / JSON fetch
  v
my_app/urls.py
  |
  v
middleware: session -> CSRF -> authentication -> messages ...
  |
  v
pc_store/views/<функциональный_модуль>.py
  |
  +--> permissions.py: авторизация операции
  +--> forms.py / http.py: проверка входных данных
  +--> selectors.py / QuerySet: выборки и агрегаты
  +--> services/: операции публикации и денег
  |
  v
Django ORM -> SQLite
FileField/ImageField -> файловая система media/
  |
  v
HTML-шаблон / JSON / поток аудио
  |
  v
Navigation заменяет #app-shell
или Actions обновляет конкретный элемент DOM
Постоянный audio остаётся за пределами #app-shell
```

### 3.2. Что здесь асинхронно

В браузере без полной перезагрузки работают:

- внутренние переходы;
- обычные формы, включая загрузку файлов;
- фильтры;
- лайки;
- подписки;
- комментарии;
- добавление и удаление треков из плейлиста;
- запросы истории и регистрации прослушиваний.

Основная серверная часть написана синхронными функциями `def` и использует синхронный ORM.

Наличие `async` в JS не означает, что Django-view является `async def`.

### 3.3. WSGI и ASGI

- `my_app/wsgi.py` экспортирует стандартное WSGI-приложение.
- В настройках указан `WSGI_APPLICATION = 'my_app.wsgi.application'`.
- `my_app/asgi.py` экспортирует стандартный `get_asgi_application()`.
- Наличие ASGI-файла не превращает существующие синхронные обработчики в собственную асинхронную реализацию.
- Channels, WebSocket, Celery, Redis и фоновых worker-процессов нет.
- Нет серверной push-доставки новых комментариев другим открытым вкладкам.

### 3.4. Как разделена ответственность

| Уровень | Ответственность |
| --- | --- |
| URLconf | Связать URL и имя маршрута с обработчиком |
| View | Получить запрос, проверить доступ, вызвать форму/сервис, вернуть ответ |
| Form | Проверить поля, файлы и пользовательские значения |
| Permission | Решить, разрешена ли операция текущему пользователю |
| Selector | Подготовить QuerySet, фильтры и агрегаты для вывода |
| Service | Выполнить составную бизнес-операцию с транзакционными гарантиями |
| Model | Структура данных, связи, ограничения и базовые свойства |
| Template | Разметка и серверное отображение |
| JS | Навигация, плеер, AJAX и состояние интерфейса |

Не все бизнес-операции вынесены в сервисы: часть логики библиотек, комментариев и модерации находится в view. Документ описывает фактическую структуру, а не идеализированную слоистую архитектуру.

## 5. Модель данных и связи

В приложении 12 конкретных доменных моделей; пользователь — стандартная модель Django. Дополнительно есть абстрактная модель `ModeratedContent`.

По умолчанию таблицы приложения называются `pc_store_<имя_модели>`. Связи M2M имеют автоматически созданные промежуточные таблицы.

### 5.1. Карта связей

```text
User
 ├── 1:1 Profile
 ├── 1:1 Artist
 │        └── 1:N Track
 │                 ├── M:N User          (likes / liked_tracks)
 │                 ├── M:N Album         (contained_in / tracks)
 │                 ├── 1:N Comment       (comments)
 │                 ├── 1:N PlayEvent     (play_events)
 │                 └── 1:N ListeningHistory
 ├── 1:1 Wallet
 │        └── 1:N WalletTransaction      (transactions)
 ├── 1:N Album                          (albums, владелец)
 ├── M:N Album                          (saved_albums / saved_by)
 ├── 1:N Follow                         (artist_follows)
 ├── 1:N Comment                        (track_comments)
 ├── 1:N ListeningHistory               (history)
 ├── 1:N PlayEvent                      (play_events)
 ├── 1:N Donation                       (donations_sent)
 └── 1:N ModerationAction               (actor)

Artist
 ├── 1:N Follow                         (followers)
 └── 1:N Donation                       (donations_received)

Comment
 └── self 1:N Comment                   (parent / replies)
```

### 5.2. User

Используется штатный пользователь Django: логин, email, хеш пароля, `is_active`, `is_staff`, `is_superuser`, группы и permissions.

Custom User-модель не заведена. В коде используются `get_user_model()` и `settings.AUTH_USER_MODEL`.

Сигнал `post_save` при создании пользователя создаёт:

- `Profile`;
- `Wallet`;
- совместимую со старой реализацией папку `Album(is_favorite_folder=True, title='Любимое')`.

Сигнал не заполняет лайки и не создаёт Artist автоматически.

### 5.3. Profile

| Поле | Тип/смысл |
| --- | --- |
| `user` | OneToOne с User |
| `role` | `listener` или `artist`; по умолчанию `listener` |
| `bio` | О себе, до 2000 символов |
| `avatar` | Необязательный ImageField, папка `avatars/` |

Свойство `favorite_album` находит старую системную папку «Любимое».

`Profile.role` — пользовательская роль слушателя/артиста. Это не роль администратора и не разрешение публиковаться.

### 5.4. Artist

| Поле | Тип/смысл |
| --- | --- |

## 6. Публичность, владение и роли

### 6.1. Три независимых понятия

1. `Profile.role`: слушатель или артист в профиле.
2. `Artist.moderation_status`: одобрена ли заявка артиста.
3. Django permissions/groups: можно ли модерировать и управлять пользователями.

Ни `Profile.role='artist'`, ни `is_staff=True` сами по себе не дают права публиковать музыку в публичном каталоге.

### 6.2. Группы и доступ

| Пользователь | Публичные страницы/аудио | Личные действия | Загрузка и релизы | Модерация | Аккаунты/балансы |
| --- | --- | --- | --- | --- | --- |
| Гость | Да | Нет | Нет | Нет | Нет |
| Слушатель после входа | Да | Да | Нет | Нет | Нет |
| Одобренный артист | Да | Да | Свои материалы | Нет, если отдельно не назначен | Нет, если отдельно не назначен |
| Группа «Модераторы» | Да | Да | Только при отдельном статусе артиста | Да | Нет |
| Группа «Администраторы» | Да | Да | Только при отдельном статусе артиста | Да | Да |
| Активный суперпользователь | Да | Да | Для авторского кабинета всё равно нужна Artist-запись | Да | Да |

Проверки находятся в `permissions.py`:

- `can_moderate(user)`: вход, активный аккаунт и superuser либо permission модерации.
- `can_manage_users(user)`: вход, активный аккаунт и superuser либо permission управления.
- `moderator_required` и `administrator_required` оборачивают view.
- Невошедшему пользователю HTML-страница предлагает вход.
- Вошедшему без прав возвращается 403.

Матрица описывает обычные группы. Возможны индивидуально назначенные Django permissions; код проверяет именно permissions, а не только названия групп.

### 6.3. Что возвращает published()

Для Track:

- `moderation_status='approved'`;
- заявка артиста `approved`;
- `artist.user.is_active=True`.

Для Album:

- `moderation_status='approved'`;
- `is_public=True`;
- владелец — одобренный активный артист;
- в релизе есть треки;
- в релизе нет треков со статусом, отличным от `approved`;
- дубли строк устраняются через `distinct()`.

Правило «только собственные треки релиза» проверяется сервисом публикации. Это не отдельное ограничение M2M-таблицы.

### 6.4. Что возвращает visible_to(user)

- Модератору — весь исходный QuerySet.
- Активному обычному пользователю — публичное плюс собственные записи.
- Гостю — только публичное.

`Track` определяет владельца через `artist.user`; `Album` — через `owner`.

Для публичных списков нельзя заменять `published()` на голый `objects.all()`.

Проверка доступа применяется и к HTML-странице трека, и к защищённой отдаче аудио.

## 7. Регистрация и профиль

### 7.1. Регистрация

`accounts.register_view` использует `RegistrationForm` на основе Django `UserCreationForm`.

Поля: `username`, `email`, `role`, `password1`, `password2`.

Пароль проверяется стандартными валидаторами Django и сохраняется через штатное хеширование.

В транзакции:

1. создаётся User;
2. сигнал создаёт Profile, Wallet и системную папку совместимости;
3. сохраняется выбранный `Profile.role`.

Затем выполняется вход:

- слушатель перенаправляется в медиатеку;
- выбравший роль артиста — на отдельную форму заявки.

Регистрация артистом не создаёт пустую заявку Artist автоматически. Для заявки нужно отдельно заполнить описание.

### 7.2. Вход и выход

- Вход обслуживается стандартным `django.contrib.auth.views.LoginView`.
- Шаблон входа — `login.html`.
- Используются Django-сессии, не JWT.
- Выход — только POST с CSRF.
- URL авторизации задаётся как `LOGIN_URL='login'`.

### 7.3. Настройки профиля

`ProfileForm` редактирует биографию и аватар.

При сохранении биография также обновляется в существующей Artist-записи этого пользователя.

Редактор профиля не является интерфейсом смены Django-прав, пароля или статуса модерации.

## 8. Заявки артистов и жизненный цикл публикации

### 8.1. Заявка артиста

Файлы: `views/artists.py`, `views/moderation.py`, `ArtistApplicationForm`.

- Вошедший пользователь отправляет биографию, максимум 2000 символов.
- Создаётся или обновляется его Artist.
- Статус становится `pending`.
- Предыдущее замечание и дата решения очищаются.
- Пока заявка не одобрена, её можно дополнить/подать повторно.
- Одобренная заявка через этот экран повторно не отправляется.

Модератор рассматривает только pending-заявку:

- `approved`: профиль получает `role='artist'`;
- `rejected`: обязательна причина;
- фиксируются время решения и ModerationAction.

Свою заявку рассматривать нельзя.

### 8.2. Зачем нужны черновики

Черновик — сохранённая незавершённая версия трека или публичного релиза.

Она:

- не появляется в публичном каталоге;
- доступна владельцу и модератору;
- не считается ожидающей проверки публикацией;
- может быть отредактирована и отправлена позже.

Кнопка «Сохранить черновик» не является публикацией и не выдаёт одобрение.

### 8.3. Статусы трека и релиза

| Статус | Смысл |
| --- | --- |
| `draft` | Сохранено без отправки на проверку |
| `pending` | Отправлено, ожидает решения |
| `approved` | Одобрено; публичность дополнительно зависит от владельца и состава |
| `rejected` | Отклонено с причиной |
| `hidden` | Ранее опубликованный материал скрыт модератором |

### 8.4. Подготовка отправки

`prepare_submission(instance, submit=...)`:

- ставит pending при `submit=True`, иначе draft;
- очищает замечание;
- очищает проверяющего и время проверки;
- обнуляет `published_at`.

Редактирование опубликованного материала не оставляет старое одобрение автоматически.

### 8.5. Проверка авторского релиза

`validate_release(album, tracks)` требует:

1. одобренного активного артиста-владельца;
2. непустого состава;
3. только его собственных треков;
4. одобрения каждого трека;
5. ровно одного трека для типа single.

Для приватного плейлиста эти правила авторского релиза не применяются.

### 8.6. Решения модератора

`review_content` выполняется транзакционно и перечитывает объект через `select_for_update()`.

| Исходное состояние | Решение | Результат |
| --- | --- | --- |
| pending | approved | Одобрение и новое время публикации |
| pending | rejected + причина | Отклонение |
| approved | hidden + причина | Скрытие |
| hidden | approved | Восстановление публикации с проверкой условий |
| hidden | rejected + причина | Отклонение |
| draft/rejected | approved напрямую | Запрещено; нужна отправка владельцем |

Свой материал одобрять нельзя, включая материал пользователя с правами модератора/администратора.

При одобрении трека проверяется существование файла.

При одобрении релиза повторно проверяются артист, состав и статусы треков.

Решение записывается в `reviewed_by`, `reviewed_at`, `moderation_note` и в ModerationAction.

### 8.7. Изменение состава

- Добавление нового трека в публичный релиз требует собственника и одобренного собственного трека.
- При фактическом добавлении релиз снова получает pending.
- Повторное добавление уже существующего трека не меняет состав.
- Удаление трека из публичного релиза переводит его в draft.
- Если трек скрыт или отправлен на повторную проверку, релиз с ним перестаёт удовлетворять `published()`.

Гарантии `select_for_update()` зависят от СУБД. В SQLite это не полноценная блокировка строки; для высокой конкуренции нельзя полагаться только на этот вызов.

## 9. Загрузка и хранение файлов

### 9.1. Формы и валидация

Источник: `forms.py`.

| Что | Правила |
| --- | --- |
| Аудио | Расширения .mp3, .wav, .ogg, .m4a; максимум 50 МБ |
| Длительность аудио | Mutagen должен прочитать положительную конечную длительность не более 86 400 секунд |
| Записываемая длительность | `max(1, round(audio.info.length))` |
| Изображение | Расширения .jpg, .jpeg, .png, .webp; максимум 5 МБ |
| Проверка содержимого изображения | Django ImageField и Pillow |
| Год при редактировании трека/релиза | От 1900 до текущего года + 1 |
| Текст песни | До 30 000 символов |

Проверка аудио не ограничивается MIME или названием файла: Mutagen разбирает содержимое.

При редактировании уже существующего трека новый аудиофайл необязателен.

После анализа поток загрузки перематывается на начало, чтобы Django сохранил файл целиком.

### 9.2. Предпросмотр в браузере

`Actions.previewFile`:

- берёт выбранный File;
- создаёт `URL.createObjectURL`;
- показывает обложку;
- для аудио назначает источник preview-аудио;
- после loadedmetadata показывает длительность;
- при смене файла/страницы освобождает object URL.

Прослушивание предпросмотра приостанавливает основной плеер. Запуск основного плеера останавливает предпросмотры.

Клиентский предпросмотр не заменяет серверную проверку.

### 9.3. Папки

| Папка относительно MEDIA_ROOT | Содержимое |
| --- | --- |
| `music/` | Аудиофайлы |
| `covers/` | Обложки треков |
| `album_covers/` | Обложки релизов/плейлистов |
| `avatars/` | Аватары |

База хранит имя файла относительно storage. Сам бинарный файл находится отдельно.

Пустое имя файла, существующая DB-запись и фактически существующий файл — три разных состояния.

### 9.4. Почему не используется audio_file.url для прослушивания

Прямой URL storage мог бы обойти проверку модерации и владения.

Поэтому аудио выдаётся через `views/playback.py:track_audio`:

1. найти Track в `visible_to(request.user)`;
2. проверить файл и размер;
3. разобрать Range;
4. вернуть поток или HEAD-ответ.

Поддерживаются:

- полный GET: 200;
- корректный одиночный диапазон: 206;
- `bytes=start-end`;
- `bytes=start-`;
- суффиксный `bytes=-length`;
- недопустимый диапазон: 416;
- HEAD без передачи тела.

Размер читаемого блока в `audio_chunks` — не более 65 536 байт.

Заголовки включают:

- `Accept-Ranges: bytes`;
- `Content-Length`;
- при частичном ответе `Content-Range`;
- `Cache-Control: private, max-age=0, must-revalidate`;
- `X-Content-Type-Options: nosniff`.

Множественные Range-диапазоны и HLS/DASH не реализованы.

### 9.5. Раздача изображений при DEBUG

В URLconf разрешена только раздача:

```text
/media/avatars/<имя_файла>
/media/covers/<имя_файла>
/media/album_covers/<имя_файла>
```

Регулярное выражение не открывает `music/` и не разрешает произвольные вложенные пути.

При `DEBUG=False` эта вспомогательная раздача изображений отсутствует; её нужно организовать отдельно при размещении.

### 9.6. Отсутствующие файлы

- `image_url` проверяет наличие изображения и возвращает пустую строку при отсутствии.
- Шаблоны показывают заглушки.
- `Track.audio_url` возвращает пустую строку при отсутствии аудио.
- Аудио endpoint возвращает 404, если файл не найден.
- `audit_media` выдаёт список проблем.

Не подбирать случайную замену по похожему имени и не удалять запись автоматически.

## 10. Каталог, поиск, фильтры и сортировки

### 10.1. Подготовка карточек

`selectors.track_cards(user, queryset=None)`:

### 10.6. Сортировки

Для треков:

- newest: `-created_at, -pk`;
- popular: `-plays_count, -pk`;
- liked: `-like_count, -pk`.

Для релизов:

- newest: `-published_at, -pk`;
- popular: `-total_plays, -pk`;
- liked: `-total_likes, -pk`.

Каталоги треков, релизов и артистов разбиты по 24 записи на страницу.

### 10.7. Особенности фильтрации релизов

- Название/артист ищутся по Album и owner.
- Год и тип относятся к самому Album.
- Жанр, настроение, темп, текст и explicit выбирают релизы с подходящими треками.
- `total_duration`, `total_plays`, `total_likes` считаются через коррелированные Subquery.
- Эти агрегаты относятся ко всему составу релиза, а не только к треку, на котором совпал фильтр.

Не заменять эти подзапросы на несколько наивных JOIN+Sum: M2M и лайки могут размножить строки и завысить суммы.

Выбранное состояние оформляет CSS `:has(input:checked)`, фокус клавиатуры —

`.track-choice`, чтобы не менять сетку треков каталога.

## 12. Асинхронная навигация и отправка форм

### 12.1. Инициализация

`app.js` один раз создаёт:

1. Player;
2. Navigation;
3. Actions;
4. вызывает первоначальный `actions.mount()`.

Navigation получает callbacks `mount` и `unmount`. Плеер не пересоздаётся.

### 12.2. Переход по ссылке

`Navigation.onClick` перехватывает обычные внутренние HTTP(S)-ссылки:

- без Ctrl/Meta/Shift/Alt;
- без другого target;
- без download;
- того же origin;
- кроме `/admin/`;
- кроме обычного перехода по hash внутри той же страницы.

`navigate`:

1. отменяет предыдущий запрос через AbortController;
2. запоминает прокрутку и при необходимости фокус;
3. делает fetch HTML;
4. разбирает документ DOMParser;
5. находит новый `#app-shell`;
6. вызывает unmount старой страницы;
7. закрывает открытые dialog;
8. удаляет исполняемые script из нового shell;
9. обновляет History API;
10. заменяет shell;
11. обновляет title и CSRF meta;
12. вызывает mount;
13. восстанавливает прокрутку и фокус.

Если подходящего shell нет, выполняется обычный переход браузера. Непрерывность аудио при таком полном переходе не гарантируется.

Back/Forward обрабатываются через `popstate`.

### 12.3. HTML-формы

Обычные формы отправляются через FormData. Это сохраняет поддержку файлов и скрытого CSRF-поля.

- GET: значения полей превращаются в query string.
- POST: отправляется FormData.
- Ответ сервера остаётся HTML, а не обязательно JSON.
- Django redirects отслеживаются fetch.
- Кнопки временно блокируются от повторной отправки.
- Для фильтров сохраняются прокрутка и фокус.
- Автоматические фильтры используют replaceState вместо засорения истории.

Формы комментариев обслуживает Actions отдельно.

### 12.4. Важный исправленный дефект: поле action

В административных формах есть:

```html
<input type="hidden" name="action" value="role">
```

Именованное поле формы может перекрыть одноимённое DOM-свойство.

Поэтому адрес и метод читаются так:

```javascript
const method = (form.getAttribute('method') || 'GET').toUpperCase();
const target = new URL(form.getAttribute('action') || location.href, location.href);
```

Не возвращать чтение `form.action` для этого сценария. Иначе «Сохранить права» и формы с полем action снова будут уходить по неверному адресу.

Регрессионная проверка находится в `tests/frontend/navigation.test.js`.

### 12.5. Ограничения подхода

- Это не отдельное SPA с JSON-роутером.
- Каждый переход обычно получает полный HTML-документ, из которого используется shell.
- Встроенные script в загруженной странице не должны быть способом инициализации компонентов.
- Новые действия следует подключать через общие модули и mount/unmount.
- Обычная полная перезагрузка восстанавливает сохранённую позицию плеера, но не непрерывный аудиопоток.

## 13. Постоянный плеер, очередь и повтор

### 13.1. Состояние Player

| Поле | Смысл |
| --- | --- |
| `audio` | Нативный HTMLAudioElement |
| `current` | Метаданные текущего трека |
| `queue` | Очередь текущего набора карточек |
| `session` | PlaybackSession для учёта прослушивания |
| `lastSave` | Ограничение частоты сохранения позиции |
| `ended` | Признак завершения текущего проигрывания |
| `repeat` | Повтор одного текущего трека |
| `pendingSeek` | Позиция для установки после loadedmetadata |
| `progress` | Слайдер перемотки |

### 13.2. Выбор и очередь

`playFromRow` собирает очередь из присутствующих в DOM `.track-row[data-url]`:

- исключает пустые URL;
- устраняет повторные ID;
- запоминает метаданные независимо от дальнейшей навигации.

Нажатие на ту же песню переключает Play/Pause.

Выбор новой песни через `select`:

- меняет current;
- создаёт новую PlaybackSession;
- задаёт источник;
- выводит метаданные;
- начинает воспроизведение;
- сохраняет состояние;
- для вошедшего пользователя отправляет историю.

Очередь не подгружает автоматически следующие страницы каталога.

### 13.3. Управление

- `play()`: запускает аудио; после завершения перематывает на 0 и создаёт новую сессию.
- `pause()`: останавливает и сохраняет состояние.
- `next()`: выбирает следующую песню очереди.
- `previous()`: после первых трёх секунд возвращает к началу; иначе переходит к предыдущей.
- `seekTo(row, seconds)`: выбирает нужную песню/позицию для таймкода.
- `sync()`: обновляет кнопки, текущую карточку и лайк.
- `updateProgress()`: время, слайдер, наблюдение сессии и сохранение позиции.

Обработчик ошибок показывает уведомление, а не пытается бесконечно переключать повреждённые записи.

### 13.4. Повтор

Повтор включается кнопкой `#player-repeat`.

- Подсветка: класс `is-active`.
- Доступность: `aria-pressed` и меняющаяся подпись.
- Настройка сохраняется в localStorage.
- Кнопка находится в `.player-tools` справа, отдельно от `.player-controls`.
- Три основные кнопки на широком экране остаются в центральной колонке.

Используется собственный `onEnded()`, а не нативный `audio.loop=true`:

1. обновить прогресс завершённой песни;
2. поставить ended;
3. если repeat включён — вызвать play;
4. иначе перейти к следующему треку;
5. если следующего нет — оставить воспроизведение завершённым.

Это позволяет создать новый playback token для каждого повторного проигрывания.

Ручной Next продолжает работать при включённом повторе.

Повтор всей очереди и shuffle отсутствуют.

### 13.5. Что хранится в localStorage

Ключ: `soundmess.player.v2`.

```json
{
  "track": {
    "id": "12",
    "title": "Название",
    "artist": "Артист",
    "url": "/track/12/audio/",
    "cover": "",
    "detail": "/track/12/comments/page/",
    "duration": 240,
    "liked": false,
    "countable": true
  },
  "position": 38.5,
  "volume": 0.8,
  "repeat": false
}
```

При восстановлении допускается аудио URL того же origin, соответствующий `/track/<число>/audio/`.

Не сохраняются:

- вся очередь;
- учтённые секунды сессии;
- признак «уже засчитано» между полными перезагрузками;
- mute как отдельное состояние.

После полной перезагрузки трек восстанавливается с позицией, но автоматически не запускается.

Не переносить сюда секреты, session cookie или платёжные подтверждения.

## 14. Подсчёт прослушиваний и история

### 14.1. PlaybackSession

Чистый JS-класс без DOM в `session.js`.

Поля:

- `token`;
- `listened`;
- `counted`;
- `pending`;
- `retryAt`;
- `anchor` с временем аудио, монотонными часами и состоянием воспроизведения.

Метод `observe` сравнивает изменение `audio.currentTime` с `performance.now()`:

- время должно двигаться вперёд;
- предыдущая и текущая точки должны относиться к воспроизведению;
- seeking не считается;
- скачок не должен превышать прошедшее время более чем на 0.75 секунды;
- добавляется минимум между медиадельтой и фактически прошедшим временем.

Пауза, ожидание данных и перемотка не должны искусственно дать 30 секунд.

### 14.2. Отправка события

`ready(now)` разрешает запрос при:

- listened >= 30;
- ещё не counted;
- нет уже отправленного pending-запроса;
- достигнуто время повтора после ошибки.

`Player.recordPlay` отправляет POST:

```json
{"playback_token": "уникальный-токен-сессии"}
```

При успехе сессия становится counted.

При ошибке следующая попытка разрешается через 5000 мс. Запрос не отправляется на каждом timeupdate без задержки.

### 14.3. Серверная обработка

`record_play`:

1. проверяет токен: непустая строка, до 64 символов;
2. находит опубликованный трек;
3. в транзакции делает get_or_create PlayEvent по токену;
4. проверяет, что существующий токен относится к этому треку;
5. только для нового события увеличивает счётчик через `F('plays_count') + 1`.

Результат: `counted` или `already_counted`.

Гостю разрешён запрос, но CSRF-защита не отключена.

### 14.4. Граница доверия

Сервер проверяет уникальность и привязку токена, но самостоятельно не доказывает 30 секунд прослушивания.

Клиент, вручную отправляющий новые допустимые токены, может обойти клиентский таймер.

Это ограничение текущей учебной реализации, а не полноценная антифрод-система.

### 14.5. История

`add_to_history` вызывается при выборе песни, а не по истечении 30 секунд.

Для того же пользователя и трека запись не дублируется чаще одного раза за 5 минут.

В медиатеке выводятся последние 20 записей, чьи треки доступны пользователю.

История и аналитика прослушиваний поэтому могут иметь разные количества.

<a id="section-15"></a>

## 15. Лайки, подписки, комментарии и лента

### 15.1. Лайк = «Любимое»

`toggle_like` работает только для опубликованного трека и вошедшего пользователя.

Предпочтительный запрос содержит желаемое состояние:

```json
{"liked": true}
```

Повтор такого запроса сохраняет состояние true.

Если ключ не передан, сервер поддерживает старое поведение переключения. Для надёжных повторных запросов использовать явный boolean.

Сервер возвращает `liked` и `like_count`.

Actions обновляет:

- кнопки в карточках;
- счётчики;
- data-liked строки;
- кнопку постоянного плеера.

В медиатеке после изменения выполняется обновление shell, чтобы список любимых песен соответствовал базе.

### 15.2. Подписки

`toggle_follow`:

- только после входа;
- только на одобренного активного артиста;
- подписаться на себя нельзя;
- желаемое состояние передаётся как `following: true/false`;
- уникальность пары обеспечивается БД.

Возвращаются `following` и `followers_count`.

### 15.3. Публичные комментарии

Endpoint `/track/<id>/comments/` поддерживает:

- GET для гостя: список видимых комментариев;
- POST после входа: создание комментария.

Сервер проверяет:

- текст — непустая строка до 1000 символов после trim;
- целочисленный неотрицательный таймкод;
- максимум — duration_seconds, а при её отсутствии 86 400;
- родитель относится к тому же треку;
- родитель и его ветка не скрыты;
- глубина нового ответа не больше 3.

Корневой комментарий имеет глубину 0, далее допустимы три уровня ответов.

Для ответа таймкод наследуется от родителя, а не от нового момента воспроизведения.

### 15.4. Откуда берётся таймкод

Actions берёт `player.timeFor(trackId)`.

Если эта песня сейчас не является текущей, возвращается 0.

Нажатие на таймкод запускает/перематывает нужную песню через `seekTo`.

### 15.5. Безопасное отображение и дерево

- Серверный HTML использует экранирование Django.
- Новые комментарии создаются в JS через DOM-элементы и `textContent`.
- Пользовательский текст не вставляется как исполняемый HTML.
- На странице трека view собирает дерево в памяти из плоского списка.
- Если скрыт родитель, его видимые по собственному флагу потомки не попадают в публичное дерево.
- JSON GET также исключает скрытые ветки.

Публичная страница обсуждения сейчас не имеет отдельной пагинации комментариев.

### 15.6. Лента подписок

`feed_view` объединяет:

- опубликованные релизы подписанных артистов;
- опубликованные отдельные треки типа single, которые не входят в опубликованный Album.

Треки, уже представленные релизом, не должны дублировать его в ленте.

Сортировка: время публикации/создания и ID, от новых к старым.

Смешанный список собирается и сортируется в Python; пагинация — по 20 записей. Для большого каталога это место потребует изменения стратегии выборки.

<a id="section-16"></a>

## 16. Кабинет артиста и аналитика

`artist_dashboard` доступен одобренному активному артисту.

Параметр `period=7` выбирает неделю, остальные значения дают 30 дней.

View:

1. строит календарный диапазон в локальной дате проекта;
2. группирует PlayEvent по `TruncDate(created_at)`;
3. дополняет отсутствующие дни нулями;
4. считает итог и максимум;
5. генерирует точки SVG;
6. получает топ-5 по `plays_count`;
7. выводит число подписчиков, собственные треки и релизы.

График не использует внешний CDN или Chart.js.

Различать:

- график — события PlayEvent за конкретный период;
- топ треков — накопительный plays_count;
- исторические значения plays_count могли существовать до появления детальных событий.

Нельзя обещать точное равенство графика и всех исторических счётчиков после переноса старой базы.

<a id="section-17"></a>

## 17. Кошелёк, переводы и идемпотентность

### 17.1. Природа средств

Кошелёк виртуальный. В пользовательских заголовках он называется просто «Кошелёк».

Деньги не принимаются через банк и не выводятся наружу.

Никаких карточных данных, API провайдера, webhook и платёжного SDK нет.

### 17.2. Формы

`PaymentForm`:

- amount: Decimal;
- минимум 0.01;
- максимум 100 000.00;
- два знака после запятой;
- token: hidden.

`BalanceAdjustmentForm` для администратора:

- amount: от -100 000 до +100 000;
- note: обязательная причина до 200 символов;
- token.

Нулевая корректировка отклоняется сервисом.

### 17.3. Подписанное подтверждение

`payment_token` создаёт подписанный Django signing payload:

```text
user     = ID текущего пользователя
purpose  = topup / donation:<artist_id> / adjust:<account_id>
nonce    = UUID hex
amount   = добавляется при подтверждении пользовательской суммы
```

Salt: `soundmess.payment`.

Срок проверки: 1800 секунд.

Подпись — защита от изменения параметров, не шифрование и не подтверждение банковской оплаты.

### 17.4. Два шага пользовательской операции

1. GET: показать форму с токеном.
2. POST суммы: проверить форму/токен, показать подтверждение.
3. В подтверждении подписать точную сумму в центах.
4. POST `confirm=yes`: проверить привязку суммы и выполнить операцию.
5. Redirect и сообщение результата.

В подтверждении amount рендерится через `form.amount.as_hidden`.

Не заменять его вручную локализованной строкой `12,34`: машинное значение суммы должно корректно пройти DecimalField.

### 17.5. adjust_balance

Сервис выполняется в `transaction.atomic`:

1. получить кошелёк;
2. зарезервировать WalletTransaction по уникальному operation_key;
3. если операция уже есть — сравнить кошелёк и сумму, вернуть прежний результат;
4. выполнить условный UPDATE;
5. перечитать кошелёк;
6. записать balance_after_cents.

Для списания UPDATE включает условие `balance_cents >= сумма_списания`.

Изменение делается через F-expression, без схемы «прочитал старое число — записал вычисленное».

### 17.6. donate

В одной внешней транзакции:

1. запретить поддержку самого себя;
2. проверить сумму, одобрение артиста и активность его аккаунта;
3. создать Donation с уникальным idempotency_key;
4. при повторе проверить совпадение donor, artist и amount;
5. списать через adjust_balance с ключом `<nonce>:out`;
6. зачислить артисту с ключом `<nonce>:in`.

Если денег недостаточно, транзакция откатывается целиком.

Повторное подтверждение той же операции не должно создавать второй перевод.

Идемпотентность не означает готовую защиту от всех сценариев высокой нагрузки: SQLite может блокировать параллельные записи, а отдельные нагрузочные тесты не реализованы.

### 17.7. Корректировка администратором

На странице пользователя администратор может изменить баланс с обязательной причиной.

Используются тот же сервис и отдельный purpose токена.

Дополнительно создаётся ModerationAction со ссылкой на WalletTransaction.

Не давать модератору это действие только потому, что он имеет is_staff.

<a id="section-18"></a>

## 18. Собственная панель модерации

### 18.1. Два административных интерфейса

- `/moderation/` — основной пользовательский рабочий интерфейс.
- `/admin/` — стандартная техническая Django-админка.

Это разные интерфейсы и не полностью одинаковые правила редактирования.

В стандартной админке Wallet, Donation, WalletTransaction и ModerationAction зарегистрированы через ReadOnlyAdmin: создание, изменение и удаление запрещены.

Остальные зарегистрированные модели могут редактироваться штатными Django-формами при наличии соответствующих прав. Не считать прямое редактирование там эквивалентом проверки через сервис публикации.

### 18.2. Страницы основной панели

| Раздел | Назначение |
| --- | --- |
| Обзор | Число pending-заявок/треков/релизов и 20 последних действий |
| Заявки | Рассмотрение Artist |
| Треки | Очередь и ранее обработанные Track |
| Релизы | Только публичные Album |
| Комментарии | Список песен и отдельное обсуждение каждой |
| Пользователи | Поиск аккаунтов и управление, только для администратора |

Заявки и очереди материалов выводятся по 20 записей, пользователи — по 30.

### 18.3. Комментарии: основной список

`moderation.comments` показывает только песни, у которых есть комментарии.

Аннотации:

- `comment_count`: всего комментариев;
- `hidden_comment_count`: число собственных флагов is_hidden;
- `last_comment_at`;
- `has_album` через Exists.

Сортировка: последнее обсуждение сначала.

Страница содержит до 24 песен.

### 18.4. Фильтры комментариев

`ModerationCommentFilterForm`:

| Параметр | Назначение |
| --- | --- |
| `q` | До 200 символов, название песни или username артиста |
| `artist` | ModelChoiceField; артисты, у которых есть песни с комментариями |
| `release_kind` | Пусто / single / album |
| `page` | Страница списка песен |

`has_album` определяется по фактическому включению в авторский Album:

- `is_public=True`;
- `is_favorite_folder=False`;
- owner совпадает с пользователем артиста песни;
- release_type не single.

Личные плейлисты и однотрековые релизы типа single не делают песню «треком из альбома».

Проверка не ограничена только опубликованными Album: панель модерации может работать и с ещё не опубликованными авторскими релизами.

Это отличается от каталожного фильтра `Track.release_type`. Не объединять эти два смысла без отдельного решения.

### 18.5. Страница обсуждения песни

`/moderation/comments/track/<id>/`:

- доступна только модератору;
- показывает комментарии именно выбранной песни;
- включает скрытые записи и ответы;
- порядок — новые сначала;
- пагинация по 30;
- показывает автора, дату, таймкод и родителя ответа;
- различает собственное скрытие и скрытие вместе с родительской веткой;
- позволяет скрыть/восстановить запись;
- сохраняет параметры фильтров при возврате.

`list_page` переносит страницу списка песен, `page` используется для страницы комментариев.

После POST изменения видимости выполняется redirect на эту же песню с сохранённым query string.

`hidden_by_parent` вычисляется для вывода и не является полем БД.

### 18.6. Управление пользователями

`update_user` принимает HTML FormData:

```text
action=role
role=member | moderator | administrator
```

или:

```text
action=active
active=true | false
```

При смене роли:

- меняются группы «Модераторы» / «Администраторы»;
- синхронизируется is_staff;
- добавляется запись журнала;
- Profile.role слушателя/артиста не меняется.

Собственные права/блокировку менять нельзя.

Суперпользователя нельзя понизить или заблокировать этим интерфейсом.

Назначение модератора не создаёт Artist и не одобряет заявку.

Этот переключатель управляет двумя штатными группами. Индивидуальные permissions и другие группы не удаляются автоматически. Поэтому при нестандартных ручных настройках эффективные права могут быть шире подписи уровня в этой форме; проверять нужно через has_perm, а не только по выбранному пункту.

### 18.7. Блокировка

Отключение `User.is_active` закрывает вход и приводит к исчезновению его публичных материалов из обычных выборок.

Сами записи и файлы при блокировке не удаляются.

### 18.8. Журнал

ModerationAction фиксирует:

- решение по заявке;
- одобрение/отклонение/скрытие материала;
- скрытие/восстановление комментария;
- изменение уровня доступа;
- блокировку/разблокировку;
- административную корректировку баланса.

В интерфейсе подписи кодов переводятся через `action_label` и `target_label`.

## 20. JSON API и форматы обмена

### 20.1. Общие требования

JSON-помощник в `http.js`:

- отправляет `credentials: 'same-origin'`;
- выставляет `Accept: application/json`;
- выставляет `Content-Type: application/json`;
- получает CSRF из `meta[name="csrf-token"]`;
- передаёт его в `X-CSRFToken`;
- оборачивает ошибки в ApiError.

HTML-формы не нужно насильно переделывать в JSON: у них отдельный путь через FormData.

### 20.2. Типовые контракты

| Операция | Тело запроса | Успешный результат |
| --- | --- | --- |
| Лайк | `{"liked":true}` | `{"liked":true,"like_count":N}` |
| Подписка | `{"following":true}` | `{"following":true,"followers_count":N}` |
| Прослушивание | `{"playback_token":"..."}` | `{"status":"counted"}` или `already_counted` |
| История | `{}` | `{"status":"success"}` |
| Добавить в Album | `{"track_id":T,"album_id":A}` | `{"status":"added"}` или `exists` |
| Удалить из Album | `{"track_id":T,"album_id":A}` | `{"status":"removed"}` |

### 20.3. Создание комментария

```json
{
  "text": "Текст комментария",
  "timestamp_seconds": 42,
  "parent_id": 123
}
```

`parent_id` необязателен.

Ответ с HTTP 201:

```json
{
  "id": 124,
  "parent_id": 123,
  "author": "username",
  "text": "Текст комментария",
  "timestamp_seconds": 42,
  "avatar": "",
  "created_at": "2026-10-22T00:00:00+00:00"
}
```

Дата в примере иллюстративная. Формат формируется через `isoformat()`.

GET того же endpoint возвращает объект `{"comments":[...]}`, а не голый массив.

### 20.4. Ошибки

`api_endpoint` обрабатывает:

| HTTP | error |
| --- | --- |
| 400 | invalid_request, invalid_json или code ValidationError |
| 401 | authentication_required |
| 403 | permission_denied |
| 404 | not_found |
| 405 | method_not_allowed; дополнительно Allow |

Обычно JSON содержит `error` и русскую `message`.

`json_body` принимает только JSON-объект. Массив, строка, число и повреждённый JSON отклоняются.

`integer`:

- не принимает bool;
- принимает int или строку целого числа;
- по умолчанию диапазон от 0 до `2**63 - 1`;
- для ID обычно задаётся минимум 1;
- для таймкода задаётся отдельный максимум.

CSRF middleware выполняется до view. Его 403 может быть обычным HTML-ответом, а не указанным JSON-контрактом.

### 20.5. Пример клиентского запроса

```javascript
const response = await fetch('/like/toggle/12/', {
    method: 'POST',
    credentials: 'same-origin',
    headers: {
        Accept: 'application/json',
        'Content-Type': 'application/json',
        'X-CSRFToken': document.querySelector('meta[name="csrf-token"]').content,
    },
    body: JSON.stringify({ liked: true }),
});
const result = await response.json();
```

В коде приложения предпочтительно использовать существующий `api()`, а не копировать обработку ошибок в каждый обработчик.

### 20.6. HTML-контракты важных форм

| Форма | Поля действия |
| --- | --- |
| Сохранить трек/релиз | `intent=submit` или `intent=draft` |
| Решение по материалу | `decision=approved/rejected/hidden`, `note` |
| Решение по заявке | `decision=approved/rejected`, `note` |
| Скрыть комментарий | `hidden=true` |
| Восстановить комментарий | `hidden=false` |
| Права пользователя | `action=role`, `role=member/moderator/administrator` |
| Доступ к аккаунту | `action=active`, `active=true/false` |
| Сохранить релиз | `saved=false` для удаления; остальные штатные отправки сохраняют |
| Подтвердить платёж | `amount`, `token`, `confirm=yes` |

Всегда сохранять скрытый csrfmiddlewaretoken при POST HTML-формы.

### 22.1. Переменные процесса

- TIME_ZONE: `Europe/Moscow`.

- STATIC_ROOT: `BASE_DIR/staticfiles`.
- MEDIA_ROOT можно переопределить окружением.

- FILE_UPLOAD_MAX_MEMORY_SIZE: 2 МБ.
- SESSION_COOKIE_HTTPONLY: True.
- CSRF_COOKIE_HTTPONLY: True.

Порог памяти для файлов не равен бизнес-ограничению аудио в 50 МБ. Не уменьшать допустимое аудио до 2 МБ на основании только имени этих настроек.

### 22.3. Middleware

По порядку:

1. SecurityMiddleware;
2. SessionMiddleware;
3. CommonMiddleware;
4. CsrfViewMiddleware;
5. AuthenticationMiddleware;
6. MessageMiddleware;
7. XFrameOptionsMiddleware.

Шаблон получает request, user, messages и собственный navigation context.

### 22.4. CSRF при навигации без полной перезагрузки

Поскольку CSRF cookie HttpOnly, JavaScript берёт токен из HTML meta, а не читает cookie.

После входа CSRF-токен может измениться.

Navigation обновляет meta из полученного HTML. Нельзя удалить этот шаг: иначе часть POST после входа начнёт получать 403.

### 22.5. Ошибки

`views/errors.py` возвращает:

- JSON для Accept, содержащего application/json;
- HTML error.html в остальных случаях.

Глобальные handlers: 403, 404, 500.

При DEBUG=True Django для некоторых ошибок показывает собственные отладочные страницы. Нельзя считать красивый error.html гарантированным ответом на любой локальный сбой.

Произвольные исключения не превращаются автоматически в ValidationError; неожиданные ошибки остаются ошибками сервера.

### 22.6. Что не настроено как производственная защита

В текущем проекте нет отдельной конфигурации production:

- HTTPS и secure cookies должны быть настроены при размещении;
- нет собственной политики CSP;
- нет rate limiting API;
- нет антиспама/антифрода;
- нет внешнего мониторинга и централизованного сбора ошибок;
- нет объектного хранилища;
- нет полноценной схемы финансового аудита для реальных платежей.

Эти пункты не повод автоматически усложнять учебный проект. Реализовывать их при появлении соответствующей задачи.

## 28. Ограничения и отсутствующие возможности

### 28.1. Сознательно не входят в текущий продукт

- Внешний импорт музыкального каталога.
- Настоящие платежи и банковские реквизиты.
- Корзина/заказы.
- Самостоятельный премиум-тариф.
- Полностью асинхронный backend.
- WebSocket и realtime-доставка чужих комментариев.
- Перекодирование аудио и HLS/DASH.
- Shuffle и повтор всей очереди.
- Полноценный production deployment.

Не восстанавливать отменённые функции только потому, что они встречались в раннем обсуждении или исторической миграции.

### 28.2. Ограничения текущей реализации

| Область | Фактическое ограничение |
| --- | --- |
| SQLite | Не предназначена здесь для доказанной высокой конкуренции записи; возможны блокировки |
| Счётчик | 30 секунд проверяются клиентом; нет полноценного серверного антифрода |
| PlayEvent | Уникальность токена защищает от повторной отправки, но не от множества новых токенов |
| Очередь | Собирается из текущего DOM, не из полного каталога |
| Перезагрузка | Позиция сохраняется, непрерывность аудио при полном reload не сохраняется |
| Вкладки браузера | Нет общего координатора плеера и live-синхронизации состояния между вкладками |
| Публичные комментарии | Дерево целиком, без серверной пагинации |
| Лента | Смешивание и сортировка записей в памяти Python |
| Порядок Album.tracks | Нет собственной позиции композиции в релизе |
| Файлы | DB-транзакция не откатывает уже записанные файлы storage |
| Очистка storage | Нет автоматического удаления старых файлов и поиска всех orphan-файлов |
| Кэш | Нет отдельной инфраструктуры кэширования |
| Аналитика | Счётчики и события старой базы могут иметь разную историческую полноту |
| URL | Некоторые JS-вызовы используют пути от корня /; размещение под URL-префиксом потребует проверки |
| Ошибки | DEBUG может показывать стандартные технические страницы Django |
| Возвраты | Choices Donation содержат refunded, но пользовательского сценария возврата нет |

### 28.3. Правила приложения не равны ограничениям базы

Прямое редактирование ORM/стандартной админкой может обойти правила, реализованные в формах и сервисах:

- владелец трека в авторском релизе;
- глубина комментариев;
- корректность перехода статуса;
- наличие аудио;
- регистрация журнала финансовой операции.

Новые изменяющие endpoints должны явно использовать соответствующие проверки.

### 28.4. Известный принцип локальных данных

Отсутствующий медиафайл не равен повреждению всей базы.

Нельзя «решать» отсутствие MP3 удалением db.sqlite3, пересозданием всех пользователей или запуском flush.
